# Операционный центр сервисной компании

## 1. Описание

Операционный центр — внутренняя информационная система для координации аварийных и сервисных работ с камерами, сетевыми коммутаторами, домофонией и другим оборудованием.

Система объединяет в одном интерфейсе:

- заявки из Service Desk;
- адресный перечень;
- реестр оборудования;
- схемы размещения и подключения;
- историю заявок и выездов;
- комментарии инженеров и координаторов;
- эталонные и актуальные изображения с камер;
- правила SLA и повторных обращений;
- события систем мониторинга;
- аналитику по проблемным объектам и устройствам.

MVP не заменяет Service Desk и системы мониторинга. Он выступает единым операционным окном поверх существующих систем и устраняет ручной перенос информации между браузерами, Excel, Google Таблицами, сетевыми папками и другими источниками.

## 2. Цели MVP

Основные цели:

1. Создать единую базу адресов и оборудования.
2. Сократить время поиска информации по заявке.
3. Уменьшить ручной перенос данных между системами.
4. Автоматизировать контроль SLA и повторных обращений.
5. Показывать историю эксплуатации устройства и объекта.
6. Позволить закрывать заявку в Service Desk из единого интерфейса.
7. Собирать данные для аналитики по проблемным адресам и оборудованию.
8. Продемонстрировать руководству сквозной рабочий сценарий.

## 3. Целевая аудитория

### Пользователи MVP

#### Координатор аварийной службы

Основной пользователь системы.

Возможности:

- просмотр очереди заявок;
- поиск объекта или устройства;
- просмотр SLA и количества повторов;
- просмотр схем, снимков и истории работ;
- подготовка задания инженеру;
- отслеживание статуса выполнения;
- получение контрольного снимка;
- закрытие заявки в Service Desk.

#### Руководитель

Возможности:

- просмотр дашборда;
- контроль соблюдения SLA;
- просмотр повторных обращений;
- выявление проблемных адресов и устройств;
- оценка рисков штрафов и неоплаты;
- просмотр загрузки и результатов работы подразделения.

### Будущие пользователи

- выездные инженеры;
- руководители подразделений;
- операторы поддержки;
- домофонисты;
- сотрудники склада;
- сотрудники снабжения;
- сетевые администраторы.

## 4. Область MVP

Первая версия ориентирована на оборудование «Безопасного города»:

- камеры;
- сетевые коммутаторы;
- связанные сетевые узлы;
- схемы размещения и подключения;
- заявки аварийной службы.

Для демонстрации используется ограниченный набор:

- один экземпляр ManageEngine ServiceDesk Plus;
- несколько контрактов;
- 50–200 устройств;
- 20–50 исторических заявок;
- несколько камер с доступным RTSP;
- реальные или обезличенные схемы объектов.

## 5. Основные пользовательские сценарии

### 5.1. Поступление заявки

1. Заявка поступает в ManageEngine ServiceDesk Plus.
2. Система получает заявку через API или импорт.
3. Заявка сопоставляется с устройством по внешнему ID.
4. Если ID отсутствует, выполняется поиск по адресу.
5. Система определяет объект, контракт и правило SLA.
6. В заявку добавляется контекст из внутренних справочников.
7. Заявка появляется в очереди координатора.

### 5.2. Обогащение заявки

Для заявки автоматически отображаются:

- адрес;
- ID и тип устройства;
- контракт;
- тип SLA;
- время до нарушения SLA;
- количество повторных обращений;
- риск штрафа или неоплаты;
- предыдущие заявки;
- история выездов;
- комментарии инженеров;
- сведения о доступе на объект;
- схема размещения;
- схема подключения;
- эталонное изображение;
- последний снимок с устройства;
- связанные события мониторинга.

Если система не может уверенно определить устройство, заявка получает статус «Требуется привязка».

### 5.3. Поиск объекта

Пользователь вводит адрес и получает:

- типы обслуживания на объекте;
- признак обслуживания домофонии;
- перечень камер и сетевого оборудования;
- схемы размещения;
- информацию о доступе;
- контакты УК, ЖКС, ТСЖ или консьержа;
- прошлые заявки и выезды;
- комментарии и материалы инженеров.

### 5.4. Поиск устройства

Пользователь вводит:

- ID устройства;
- IP-адрес;
- часть адреса;
- модель;
- номер контракта.

Система показывает карточку устройства, сетевые параметры, расположение, эталонный снимок, историю заявок и связанные устройства.

### 5.5. Контроль SLA

Для каждой заявки система:

1. Определяет применимое правило по контракту и типу устройства.
2. Начинает отсчёт от времени поступления заявки в СПУЗ.
3. Рассчитывает крайний срок выполнения.
4. Показывает прошедшее и оставшееся время.
5. Подсвечивает приближение нарушения.
6. Считает повторы за установленный период.
7. Показывает риск штрафа или неоплаты.

Примеры правил:

- камеры типа 3 — SLA 24 часа;
- контракт 92, камеры типа 2 — SLA 120 часов, четыре повтора за три месяца;
- контракт 71, камеры типа 2 — SLA 120 часов, четыре повтора за один месяц.

Правила должны храниться в справочнике, а не быть жёстко привязаны к интерфейсу.

### 5.6. Передача задания инженеру

Координатор формирует сообщение, содержащее:

- номер заявки;
- адрес;
- ID устройства;
- описание проблемы;
- приоритет;
- оставшееся время SLA;
- сетевые настройки;
- сведения о доступе;
- ссылку на карточку;
- схему размещения.

Для MVP достаточно:

- скопировать сообщение;
- открыть ссылку на отправку через используемый мессенджер;
- сохранить факт передачи задания.

Прямая интеграция с мессенджером не обязательна.

### 5.7. Работа инженера

Инженер открывает адаптивную веб-страницу с телефона.

Инженер может:

- найти объект по адресу;
- найти устройство по ID;
- посмотреть схему;
- посмотреть сетевые параметры;
- посмотреть эталонное изображение;
- прочитать комментарии;
- изменить рабочий статус;
- добавить комментарий;
- приложить фото или видео;
- указать результат работ.

Офлайн-режим в MVP не требуется.

### 5.8. Проверка изображения

Система позволяет:

- запросить актуальный кадр из RTSP-потока;
- сохранить кадр с датой и временем;
- показать эталонный и актуальный снимки рядом;
- получить контрольный снимок перед закрытием заявки;
- приложить контрольный снимок к результату работ.

Полноценное воспроизведение RTSP в браузере не входит в MVP.

### 5.9. Закрытие заявки

1. Инженер добавляет результат работ.
2. Координатор проверяет комментарий и вложения.
3. Система запрашивает контрольный снимок.
4. Координатор подтверждает закрытие.
5. Итоговый комментарий передаётся в ServiceDesk Plus.
6. Контрольный снимок добавляется как вложение.
7. Статус исходной заявки изменяется.
8. Результат сохраняется в локальной истории.

Если Service Desk недоступен, операция получает статус «Ожидает синхронизации» и может быть повторена.

### 5.10. Массовая авария

Система группирует связанные заявки по следующим признакам:

- общий ОПМ;
- общий коммутатор;
- общий адрес или группа адресов;
- общая подсеть;
- близкое время возникновения;
- общий триггер Zabbix;
- общий оператор последней мили.

Координатор видит один массовый инцидент и перечень затронутых заявок.

В MVP допускаются:

- простая автоматическая группировка;
- ручное объединение заявок;
- ручное исключение заявки из группы.

### 5.11. Аналитика

Система отвечает на вопросы:

- какие адреса создают больше всего заявок;
- какие устройства чаще всего выходят из строя;
- где происходит больше всего повторных выездов;
- сколько заявок закрыто в пределах SLA;
- какие заявки находятся в зоне риска;
- какие устройства приближаются к порогу неоплаты;
- на каких объектах отсутствуют схемы;
- у каких камер отсутствуют эталонные изображения;
- какие заявки не удалось связать с реестром оборудования.

## 6. Экраны MVP

### 6.1. Дашборд

Показатели:

- открытые заявки;
- просроченные заявки;
- заявки с приближающимся SLA;
- повторные заявки;
- устройства в зоне риска;
- массовые аварии;
- непривязанные заявки;
- проблемные адреса.

### 6.2. Очередь заявок

Функции:

- фильтрация;
- сортировка по приоритету;
- поиск;
- просмотр SLA;
- просмотр количества повторов;
- переход к заявке;
- переход к устройству или объекту.

### 6.3. Карточка заявки

Содержит:

- данные исходной заявки;
- SLA;
- историю обращений;
- историю выездов;
- объект;
- устройство;
- схемы;
- снимки;
- комментарии;
- вложения;
- события мониторинга;
- действия по передаче и закрытию.

### 6.4. Карточка объекта

Содержит:

- адрес;
- координаты;
- типы обслуживания;
- информацию о доступе;
- контакты;
- оборудование;
- схемы;
- документы;
- заявки;
- выезды;
- комментарии.

### 6.5. Карточка устройства

Содержит:

- идентификаторы;
- модель;
- сетевые настройки;
- контракт;
- принадлежность;
- расположение;
- связанные устройства;
- состояние;
- эталонный снимок;
- последний снимок;
- историю заявок.

### 6.6. Аналитика

Содержит:

- статистику SLA;
- статистику повторов;
- проблемные адреса;
- проблемные устройства;
- статистику по контрактам;
- полноту справочных данных.

## 7. Что не входит в MVP

- полноценный складской учёт;
- выдача и списание ТМЦ;
- автоматический расчёт ЗИП;
- оптимизация маршрутов;
- автоматическое назначение инженеров;
- замена Service Desk;
- поддержка всех подразделений компании;
- полноценная система управления конфигурациями;
- массовое управление оборудованием;
- мобильное приложение;
- офлайн-режим;
- постоянная ретрансляция видео;
- компьютерное зрение;
- универсальный парсинг любых городских порталов.

## 8. Ограничения

- срок разработки демонстрационного MVP — около одной недели;
- первоначально системой пользуются координатор и руководитель;
- размещение выполняется во внутренней инфраструктуре;
- доступ к камерам осуществляется из закрытой сети;
- внешнее облачное хранилище не используется;
- качество сопоставления зависит от качества исходных данных;
- управляющие действия с оборудованием требуют отдельного согласования.

## 9. Критерии готовности

MVP готов к демонстрации, если:

- можно импортировать объекты и устройства;
- можно найти объект по адресу;
- можно найти устройство по ID или IP;
- заявки поступают через API или демонстрационный импорт;
- заявка связывается с устройством;
- отображается история обращений;
- рассчитываются SLA и повторы;
- отображаются схема и эталонный снимок;
- можно получить актуальный кадр с тестовой камеры;
- инженер может оставить комментарий;
- координатор может подготовить закрытие;
- комментарий и вложение отправляются в Service Desk либо ставятся в очередь синхронизации;
- основные показатели отображаются на дашборде.

## 10. Метрики результата

Для оценки MVP используются:

- среднее время поиска информации по заявке;
- доля автоматически связанных заявок;
- количество действий координатора до передачи задания;
- доля заявок с рассчитанным SLA;
- количество обнаруженных повторов;
- количество объектов без схем;
- количество устройств без эталонного изображения;
- количество заявок, закрытых из единого интерфейса;
- количество предотвращённых нарушений SLA.
